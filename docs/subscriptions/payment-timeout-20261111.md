# 30分钟支付订单失效与席位释放

用户最终要求：创建订单30分钟内未完成支付，站内自动取消支付资格并释放席位。取消／过期订单不能因回调或主动查单重新变成成功，不能补发套餐或转余额。此规则替代原先为迟到付款永久保留易支付／虎皮椒库存的策略；不是原工作区5分钟支付过期草稿的合入。

## 规则

- `SubscriptionPendingOrderTTLSeconds=30*60`。限量库存仅计成功付款＋展示销量＋创建时间距今不足30分钟的pending订单。canceled/expired/failed订单不占席位，后台清理延迟不影响30分钟的库存边界。
- 每分钟的既有主节点订阅维护任务自动分批处理超时订单；订阅订单先取套餐锁、再订单锁，同事务更新其充值账单镜像。钱包订单另行清理，避免订阅镜像与订阅单独过期。启动时即执行一次；不需要页面轮询或用户刷新才能释放。
- 创建时间恰好30分钟时失效；30分钟内pending仍能正常完成，成功订单幂等回调不受后续超时清理影响。手动取消立即结束支付资格并释放库存。编辑总量、下单、支付、取消与过期使用一致锁序，避免超卖／死锁。
- 前端虎皮椒倒计时与服务端统一30分钟。过期／取消订单隐藏“去支付”，repay接口拒绝续付或生成新链接；需要购买必须用新订单。原支付协议的Stripe会话和Pancake可配置有效期也设为30分钟。
- 支付回调／查单在发权益前锁定订单，已取消、已过期或跨30分钟的pending不得恢复成功。订阅与钱包均不发额度、不发权益、不发返利。若收到经过现有验签或认证查单确认的收款，只在原关闭状态保存异常收款证据、账单标记`payment_received_after_close`，发系统错误日志，订单列表显示“已取消订单收到异常付款，请联系客服核对处理”。原始付款凭证保留，重复通知不重复处理；不擅自退款或转余额。

站内取消与支付平台收款是两个状态域。当前虎皮椒V1.1公开API只有创建／查询／退款文档，未找到可验证的统一关单接口；本次不编造调用一个未确认的关单URL，也不声称能撤销用户已保存的外部支付链接。平台收到旧链接的实际入账必须作为异常核对处理，不能伪造为“从未收到付款”。用户若需要网关层绝对禁止旧链接收款，需由支付服务商提供该账户可用的关单接口；已有站内取消、席位释放和禁止恢复成功均独立执行，不因缺少网关关单能力继续占位。

## 历史数据

不删除订单、不更改用户余额／订阅／售价／销售总量，不人为增加库存。应用启动后自动把旧pending订单标记expired，原已取消订单原状态保留但不再占库存。例如套餐36核对时总量20、实际已售6、展示0、1笔11月9日已取消订单：新逻辑应显示剩余14、占位0，售出量仍6。若期间新增真实付款或新待支付订单，则按真实最新数据计算，不强制写成14。
