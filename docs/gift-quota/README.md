# 赠送额度与永久余额（已上线，2026-11-10）

## 用户行为

- 付款充值继续计入账户余额，永不过期；兑换码保持原有永久余额语义，不能凭兑换码判断用户是否付费购买。
- 管理员增加额度时选择「赠送余额」或「账户余额」，默认赠送。赠送按笔保留原始金额、剩余金额、赠送时间及到期时间，每笔赠送满30×24小时到期。
- 使用钱包时优先扣到期最早的赠送，再扣永久余额。套餐选择规则不变；原本可使用钱包的功能继续可使用两种额度。
- 网页钱包只区分账户余额和赠送余额，不展示或细分管理员、注册、签到等赠送来源。分别显示两种余额、最近到期时间和赠送额度记录。记录显示原始赠送、已用、剩余、过期金额及赠送/到期时间，过期后仍保留，分页查询只允许本人。
- 预扣、补扣、部分退款、异步任务退款及旧版MJ退款携带原请求标识。退款恢复原资金来源，过期赠送退款仍计入过期，不变成永久余额、不重置有效期。
- 注册初始奖励、受邀奖励、签到奖励和邀请返利转入钱包均进入30天赠送额度。尚未转入钱包的邀请返利维持原规则。

## 数据与扣费

`users.quota` 保持原API可用总额度的兼容语义；永久余额为总额减有效赠送余额。新增 `users.gift_wallet_enabled`、`gift_quotas`、`wallet_gift_allocations`；旧MJ记录新增私有的 `wallet_request_id`，通用任务使用原私有JSON字段存储请求标识。原始OAuth奖励收据和日志不改写。

赠送、过期、钱包扣款及资金来源分配在同一用户行锁事务内完成。钱包金额改为即时落库，不能再以待刷新的Redis/批量余额放行；令牌额度的既有批量逻辑保留。认证缓存机制保持不变，实际钱包校验重新读取有效余额。后台每分钟分批过期，余额查询、预扣和扣费也同步校验到期边界。多副本由用户行锁序列化。

因此钱包写入会比旧批量模式更频繁。功能回归覆盖并发扣款和事务一致性，没有进行生产容量压测。Redis余额只作缓存提示，数据库记录是实际资金依据。
